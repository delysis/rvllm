# ANE compiled-cache loss: limits and safe recovery

2026-09-16. Source-only addendum for M4 Max / macOS 15.6, build 24G84, AppleNeuralEngine 8.600.2. No hardware, private-selector calls, builds, cache access/mutation, or production edits. The qualified single-input/output ABI and current source-cleanup policy remain unchanged.

**Finding:** cache eviction is an expected platform capability, but no inspected primary source establishes a numeric count, byte quota, expiry interval, or persistence guarantee for this private path on 24G84. Treat the daemon cache as recoverable acceleration, not durable model storage. The observed 62/162 and 66/162 inventories do not establish a 64-entry limit. The approximately 119 compiler-call issue is a separate process/runtime constraint, not a demonstrated disk-cache quota.

## Evidence and applicability

**Official behavior, public Core ML.** Apple explains that device-specialized artifacts are keyed by model path/configuration and normally survive launches and reboots. The OS can delete them when storage is low, after an OS update, or when the compiled model is deleted/modified. Apple recommends keeping a model loaded across a run of predictions. No threshold, eviction ordering, minimum lifetime, or pinning API is promised. This is authoritative for the supported Core ML lifecycle; it does not identify which private `_ANEInMemoryModel` maintenance rule affected rvllm. [WWDC23 session 10049, model lifecycle discussion](https://developer.apple.com/videos/play/wwdc2023/10049/).

**Extracted binary evidence, not executed behavior.** blacktop/ipsw-diffs revision `826027d4463eab23b96c4325fa7154ef43c75acd` compares **iOS 18.5 / 22F76 against iOS 26.0 beta / 23A5260n**, with aned versions **370.56 → 380.7**. Its old-side `aned` contains CacheDelete registration, urgency/purge handling, and periodic-maintenance strings. The comparison removes these strings from that binary; it does not prove that functionality disappears from the platform. The old-side `ANEStorageMaintainer` extraction also contains `kANEFRetainModelsWithoutSourceURLKey` and `model.retain`. These establish internal maintenance/retention concepts, not a callable retention contract or an exact macOS 24G84 policy. No numeric quota can be read from these names. Do not create marker files or set inferred option keys. **A distinct cache route.** Bryngelson describes e5rt's `cache_bundle_location` and `bundle_cache_apfs_purgeable`, the latter marking bundles reclaimable under storage pressure. The account's direct measurements are M1/M5, with additional decompiled evidence. e5rt's configurable bundle cache is not rvllm's qualified private model path; this is no basis for transferring an option or changing backends. Its reported kernel mapping LRU and 60 concurrently live program handles concern device mappings/residency, not retained compiled files. [arXiv:2606.22283v1 §5.2.1](https://arxiv.org/html/2606.22283v1#Ch5.S2.SS1), [§28.3](https://arxiv.org/html/2606.22283v1#Ch28.S3), [§32.2](https://arxiv.org/html/2606.22283v1#Ch32.S2).

**Current implementation precedent.** oMLX revision `e27e2633a650c25c590e3c1f6d1a74a74f0d494d` checks `compiledModelExists` at startup, skips compilation on a hit, and serializes probe/staging/load by descriptor identity with a bounded cross-process lock. It preserves the framework-selected temporary path and deletes source staging on unload. Its comment attributes a model-URL override failure to macOS 27, so that explanation is not a 15.6 result. There is no demonstrated daemon retention guarantee. Its purge-and-recompile fallback is upstream behavior, **not recommended here**: rvllm should retain its narrower confirmed-miss handling and stop on other load errors. ## Safe mitigation now

1. **Continue bounded, serialized confirmed-miss recovery.** Fix signing identity, OS/framework identity, graph/options/source digests; enforce total and per-process compile budgets, time budget and disk floor. A cache/load error other than a classified absence stops recovery. Do not purge or force recompilation of hits.
2. **Verify net progress.** Record the exact pre/post hit sets, not just successful compile totals. After each bounded batch, use the already qualified strict inspection/load path to establish whether older repaired entries survive. If repaired entries repeatedly disappear, stop the repair loop instead of treating successful compiles as completion. Inspection loads themselves can affect recency; label them as interventions.
3. **Then retain the warm owner.** Require a final successful all-program load before accepting prompts, and reuse that same-thread owner. This avoids repeated startup dependence; it is not a promise that its disk cache is pinned. Preserve current verified source cleanup and one-I/O ownership.
4. **Keep recovery inputs reproducible.** A small durable manifest plus checkpoint and deterministic packing suffices. A separately budgeted prepared-source store can reduce host work later, but cannot guarantee daemon retention and must not be confused with compiled artifacts. Publish startup readiness, miss count and bounded repair cost explicitly.

No additional cache selector, retention marker, e5rt flag, multi-I/O experiment, or recurring keepalive is justified by this evidence.
