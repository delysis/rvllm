# Persistent Gemma 4 Metal/ANE worker

2026-09-14. Read-only design review; no code edits, builds, or accelerator operations. Parent evidence: retained Metal+ANE capture matched 144 state/KV files, used zero compilations, and observed approximately 36.7 GiB peak client RSS. Throughput qualification is separate; this observation does not establish a causal coexistence penalty.

**Use `EngineHandle::spawn_with_factory` with one concrete `InferenceWorker` owning both backends.** The existing API already provides the required serialization and thread confinement. First expose it through a persistent CLI input loop; then add a thin `rvllm-serve` adapter using the same handle. Keep decode ownership and the qualified generation sequence in one runtime implementation.

## Minimal per-request flow

Extract the sequence currently in [`rvllm_disaggregated_infer`](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/bin/rvllm_disaggregated_infer.rs:243) into a concrete runtime worker. Prepare both backends once inside the factory; strict cached INT8 with compile budget zero should be the first supported configuration. Eager ANE loading makes successful factory return mean both devices are ready.

For each `generate`:

1. Reject empty/invalid vocabulary IDs, non-greedy sampling using [`SamplingParams::is_greedy`](/Users/george/Downloads/rvllm/v3/crates/rvllm-sampling/src/params.rs:25), and unsupported budgets before hardware. Check `prompt_len + max_output_tokens - 1 <= context_capacity` with checked arithmetic, and prompt length against prepared `max_batch_tokens`. The first sampled token does not itself consume an additional KV position.
2. Create one request-local `PagedKvPool` and chain using `output.request_id()`, construct the existing full-prompt `BatchPlan` and handoff, and call `prefill_for_ane`. A local pool is sufficient for serialized full prompts; it naturally drops on every return. Keep the chain alive through synchronous collection/export. Check returned request ID and next position.
3. Emit Metal's first token with `text: None`. Stop immediately on EOS or output limit. Otherwise import all 48 layers, then drop the host snapshot. [`import_prefill`](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/gemma_ane_decode.rs:468) validates the complete snapshot and resets each layer's cache/position; it already supports replacing a previous request. Do not carry prior ANE KV into a new prompt.
4. Check cancellation before prefill, after its synchronous completion, before import, and between ANE steps. Emit actual decode results, enforce positions, and stop on loaded EOS IDs or length. Return `GenerationOutcome`; the request API owns `Finished` delivery. No artificial stop-token invocation or extra decode is needed.

Unlike the current CLI, this must execute **prefill A → ANE A → prefill B → ANE B**. Its current `starts` vector batches all prefills first, so keeping that loop would not support prompts arriving after initialization and would retain unnecessary host KV snapshots. Retain weights/scratch only; per-request pool, snapshot, text state, and receipts are transient.

## Configuration and lifecycle hooks

Add a small immutable route-specific config: checkpoint path, explicit BF16 metallib path, qualified capacity (64/1024), maximum prompt tokens, INT8 cached weight plan, compile budget (zero by default), and explicit private-ANE opt-in. `AppleEngineConfig` supplies queue capacities and host policies but has no concrete Metal scratch/context/kernel selectors today. Use `CachePolicy::Disabled` for both engine and requests initially; this means no cross-request prompt cache, not eviction of ANE compiled artifacts. `GenerateRequest::new` defaults to `MemoryOnly`, so explicitly narrow it.

The library configuration gap is real: the CLI currently [sets environment variables](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/bin/rvllm_disaggregated_infer.rs:211), Metal [sizes from environment](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/gemma4_model.rs:2016), and [MMA selection reads environment during routing](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:49). Introduce a resolved immutable Metal options value and thread it through **both arena sizing and state creation**, plus pipeline/routing policy and numeric ABI identity. Include dtype, context, batch tokens, one sequence, large-model opt-in, and MMA/accumulation choice. Do not size for the first prompt and later accept a longer one. The CLI may translate its startup options/environment once; worker/factory/server library code must not call `set_var` or restore process environment on drop.

Resource paths can reuse the explicit metallib constructor. The packaged path [`from_model_package_path`](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/apple_metal_backend.rs:1828) authenticates assets, but this research checkpoint should not be presented as a validated shipping package. `resource_bundle_path` alone does not currently configure this new factory.

Add an explicit Metal-prefill/ANE-decode backend policy/report identity: current `BackendKind` has only Metal and CoreML. Private ANE must not silently become the meaning of `Automatic` or be reported as public CoreML. Record preparation separately, prefill including export/import with a defined timing scope, ANE decode time, batch size 1, cache tier None, zero saved tokens, and unknown memory/thermal values unless measured.

[`handle_memory_pressure`](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/request_api.rs:703) is acknowledged on the owner thread, but the serialized loop handles it only between requests. Document that latency; do not claim immediate interruption. A minimal critical-pressure policy can drop backend owners at the next safe boundary, mark the route unavailable, and require explicit reinitialization. This is not daemon-cache eviction. On accelerator execution failure, stop admitting hardware work until explicit recovery; `worker_loop` otherwise continues after ordinary errors. Health must distinguish a running thread from a ready backend.

## CLI first, then server

**Persistent CLI:** create the factory once, read successive stdin/line or existing prompt inputs, encode through the existing formatter, submit, and drain each handle. Keep one frontend tokenizer. Decode token IDs in this adapter with a fresh `IncrementalTextDecoder` per request; on `Finished`, perform full `decode(ids,true)`, require the streamed text to be its prefix, and emit the remaining suffix. This preserves the [existing CLI tail handling](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/bin/rvllm_disaggregated_infer.rs:429) without extending `TokenEvent` or fabricating a token. The worker needs EOS IDs, not a duplicate tokenizer.

**Server:** add an explicitly gated disaggregated backend behind `macos-private-ane-research` on macOS/aarch64; `rvllm-serve` currently exposes only its public `apple` feature. Its [`CompletionBackend: Send + Sync`](/Users/george/Downloads/rvllm/v3/crates/rvllm-serve/src/lib.rs:189) should contain only the clonable engine handle, tokenizer/config, and plain-data health. Existing HTTP threads and [`BackendStreamEvent`/SSE writer](/Users/george/Downloads/rvllm/v3/crates/rvllm-serve/src/lib.rs:748) can remain. Socket-write failure drops/cancels the request handle. No backend mutex should contain Metal or private ANE objects.

Do not reuse the old server's [hardcoded BOS-2 tokenizer](/Users/george/Downloads/rvllm/v3/crates/rvllm-serve/src/lib.rs:1246), its [environment guards](/Users/george/Downloads/rvllm/v3/crates/rvllm-serve/src/lib.rs:962), or its generic Metal-only capacity assumptions. Reuse the new CLI adapter's exact template, budget, and final-text handling. Initially expose ordinary single-user prompt completion; no claim of arbitrary message-history/chat-template support.

Acceptance order: source/unit tests for request validation, thread identity, cancellation/backpressure, EOS-first/length-one, exact boundary arithmetic, and UTF-8 tail; then parent-run A→B→A with distinct prompt lengths and fresh-reference outputs, zero new compiles, bounded memory, cancellation followed by a clean request, and finally two queued HTTP requests/disconnect. The retained capture is valuable evidence, but does not yet prove this interleaved successive-request lifecycle.
