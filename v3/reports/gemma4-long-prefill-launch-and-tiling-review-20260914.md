## 1. Pointwise launch audit

`gelu_mul_f16` uses only global `(token,dimension)` coordinates and independent per-element math; it has no barriers, SIMD operations, or threadgroup storage. Keep its existing grid `(M,I,1)` and expression, but test **threads per group `(1,256,1)`**. Adjacent lanes then operate on adjacent dimensions of the same token. `I=15360` is exactly divisible by 256. The existing embedding launcher already uses this orientation. [GELU kernel](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:1630), [current one-thread launch](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:2340), [embedding precedent](/Users/george/Downloads/rvllm-runtime/src/apple_metal_backend.rs:3005)

Across 48 layers, M652 currently dispatches **480,706,560 GELU threadgroups**; the proposed grouping uses 1,877,760 with identical logical element coverage. This is a 256-fold group-count reduction, **not** a predicted 256-fold speedup. At M84 the respective counts are 61,931,520 and 241,920.

Existing grouping is appropriate for a separate numerical optimization, not launch-only cleanup. Embedding already groups up to 256 contiguous channels. ## 2. Attention: substantial opportunity, arithmetic change required

Current prefill attention dispatches **one thread per group per query/head**. That thread computes serial D256/512 dot products and PV updates, retaining a private `float out_vals[512]`. Actual register spilling is unmeasured, but the scalar dimension loop and one-thread group are explicit. [Kernel](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:1538), [launch](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:1468)

The lowest-complexity rewrite is **one 32-lane SIMD group per `(query,head)`**, with separate D256 and D512 specializations. Each lane keeps 8/16 Q values and FP32 output accumulators; compute partial QK across those dimensions and `simd_sum` once per KV token, then update online max/sum/PV. Launch grid `(M,16,1)`, group `(32,1,1)`. Adapt the existing [SIMD decode pattern](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:1442), but do not reuse its D≤256 guard/arrays for global D512. Preserve absolute positions, causal/window endpoints, arbitrary page IDs, head mapping, attention scale 1.0, BF16 inputs/output, and FP32 softmax/PV. This changes QK summation order and requires numerical qualification.

Current upstream sources do **not** support assuming a wholesale fused-attention transplant wins:

- MLX `d9add9d11f3154111a4c85f267ec2fd307ecd18e` instantiates D256 full attention as **BQ32/BK16, four SIMD groups**, including BF16. Nevertheless, its dispatcher defaults long D256 to the **unfused** route, and full fused support excludes D512. Its NAX exception concerns sufficiently large queries on newer hardware, not this M4/M84–652 case. [Instantiations](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/kernels/steel/attn/kernels/steel_attention.metal#L14), [support and selection](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/scaled_dot_product_attention.cpp#L735)
- llama.cpp `7cf1c54a96d4e950ffa614b94babf762803a8de7` supplies native BF16 D256/D512 flash kernels, with **Q8/KV64 tiles and 128/256 threads** respectively. They add padding/mask preparation and nontrivial staging. Its BF16 type bundle includes half output-matrix fragments, so this is not our FP32 online-accumulator numerical path verbatim. Treat it as a later blocked-attention design reference. [Tile constants](https://github.com/ggml-org/llama.cpp/blob/7cf1c54a96d4e950ffa614b94babf762803a8de7/ggml/src/ggml-metal/ggml-metal-impl.h#L119), [dispatch](https://github.com/ggml-org/llama.cpp/blob/7cf1c54a96d4e950ffa614b94babf762803a8de7/ggml/src/ggml-metal/ggml-metal-ops.cpp#L3331), [BF16 types and instantiations](https://github.com/ggml-org/llama.cpp/blob/7cf1c54a96d4e950ffa614b94babf762803a8de7/ggml/src/ggml-metal/kernels/fa.metal#L906)

For perspective, the packed projections perform approximately 1.83/14.23 TFLOP at M84/652; causal QK+PV approximately 0.0033/0.195 TFLOP, excluding softmax and other elementwise work. These are shape calculations, not timing shares: scalar attention can still dominate despite only approximately 0.18–1.37% as much arithmetic. Measure after pointwise fixes.

## 3. MMA32 has reuse opportunities, not an obvious thread-count defect

The current [32×32×32 kernel](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:509) uses four SIMD groups, native BF16 operands, four FP32 accumulator fragments per group, two threadgroup barriers per K32, and 8 KiB of static threadgroup staging including output. Its 128-thread count is conventional. Even N3840 has 360 groups at M84 and 2,520 at M652; low grid parallelism is not established.

The next matrix candidate should be **BM32/BN64/BK32, 128 threads**, preserving current M-tail behavior. Arrange four groups as 2×2, each computing 16×32 with eight accumulator fragments. This doubles reuse of A across output channels. Then compare BM64/BN32/BK32 for M≥128 to increase weight reuse across prompt rows. All current projection N/K dimensions are multiples of 64; only M needs a tail path. Keep aligned N/K loads separate from the guarded final M tile.

llama.cpp uses the corresponding **64 output-channel ×32 token ×32 K** tile with eight FP32 accumulator fragments per group, vector loads, BF16 operands, and direct full-tile stores. MLX offers 64×32×32 and 64×64×16 choices by device/shape, padded shared strides, and vectorized safe/aligned loaders. Its conventional `BlockMMA` loads operands into accumulator-type fragments, so copy tiling ideas without silently changing our native BF16 operand path. [llama matrix tile](https://github.com/ggml-org/llama.cpp/blob/7cf1c54a96d4e950ffa614b94babf762803a8de7/ggml/src/ggml-metal/kernels/mul_mm.metal#L160), [MLX dispatch](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/matmul.cpp#L90), [MLX padding](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/kernels/steel/gemm/gemm.h#L38), [loader](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/kernels/steel/gemm/loader.h#L73), [fragment types](https://github.com/ml-explore/mlx/blob/d9add9d11f3154111a4c85f267ec2fd307ecd18e/mlx/backend/metal/kernels/steel/gemm/mma.h#L480)

A 32×64 candidate with operand row stride40 and float output tile uses 15,872 bytes of shared staging; more accumulators/shared memory may reduce occupancy. Padding by eight BF16 elements and vectorized aligned loads are separate comparisons, not guaranteed improvements. Defer 64×64 and BK64, double buffering, split-K, or attention fusion until a simpler candidate wins. Keep QKV output FP32 before RMS, gate/up BF16 before GELU, and O/down BF16 before their separate RMS operations. No new activation fusion or BF16→FP16 narrowing.
