# ANE runtime compression controls: bounded source audit

2026-09-14. Read-only source/web research; no hardware, builds, selectors, or cache inspection. Local results below are the parent task's observations, not measurements performed by this audit.

**Conclusion: no verified compiler/model option was found that forces compressed runtime weight storage on rvllm's macOS 15.6 `_ANEInMemoryModel` route.** The inspected implementations select compression through the MIL weight expression. Internal compiler capability gates exist, but they are not demonstrated callable settings. Continue the existing INT8 full-model qualification without speculative flags.

## What determines streaming, according to the sources

Apple explicitly says some backends expand weights before execution, while others reconstruct them during execution and reduce memory traffic. Palettization is its preferred ANE compression family; W8A8 is a distinct path with faster INT8 arithmetic on M4. There is no promise that a smaller model implies lower runtime traffic. [Apple overview](https://apple.github.io/coremltools/docs-guides/source/opt-overview.html).

Apple recommends **per-channel** scales for ANE weight quantization; the per-block INT4 recommendation mainly concerns GPU execution. It says JIT palette decompression is more likely on ANE from macOS 14, and that increasing the number of grouped codebooks can hurt performance. These are model/device-dependent guidelines, not retention switches. [Quantization performance](https://apple.github.io/coremltools/docs-guides/source/opt-quantization-perf.html), [palette performance](https://apple.github.io/coremltools/docs-guides/source/opt-palettization-perf.html).

The primary reverse-engineering guide describes a streaming master capability at HAL offset `0x48f`, format capabilities around `0x520–0x539`, immutable weights, unit strides, and constraints involving dilation/overlap. It identifies compiler-internal stream-versus-fold decisions. **Those offsets are not options to set**, and the inspected account does not prove an ABI or selectable override on our exact OS. Our static, unit-stride 1×1 FFN has no obvious mismatch with the described eligibility conditions; that is an inference, not verified lowering. [Pinned mechanism](https://github.com/sbryngelson/ane-guide/blob/9eb1afe95cdc766d7bec4d1d02d4918ef6268ece/part-7-toolchain/25-compression-internals.md#L137).

## Performance evidence and its limits

- **Our M4 Max, actual Gemma FFN:** INT8 3.671 ms versus original FP16 4.246 ms and reconstructed FP16 4.324 ms; earlier scalar LUT4 approximately 1.24× versus reconstruction. These component comparisons establish a useful runtime effect under their recorded conditions. Neither proves the amount of DRAM traffic or identifies lowered weight sections. LUT4 failed full-model quality; INT8 full-model qualification remains in progress at writing.
- **Published M4 H16G, synthetic W8A8:** 128 convolutions with 512 channels and 64×64 spatial input: 14.8→7.8 ms, 1.88×. The benchmark explicitly inserts activation quantize/dequantize between convolutions. This changes activation precision and has extensive spatial reuse; it is not a weight-only, one-token FFN comparison or a Gemma accuracy result. [Results](https://github.com/maderix/ANE/blob/d91c9845c0784dec7753048954fc6d0e8411fe29/README.md#L73), [MIL](https://github.com/maderix/ANE/blob/d91c9845c0784dec7753048954fc6d0e8411fe29/ane_int8_bench.m#L51).
- **ANEForge compression benchmark:** its checked-in 8192×4096, batch-1 result is 0.5226 ms FP16, 0.5215 ms INT8, 0.3137 ms LUT4. The JSON lacks machine/OS identification, so it must not be attributed to our M4 or automatically to M5. Its byte ratios are explicitly `weights.bin.stat().st_size`: **source blobs, not lowered weights**. [Results](https://github.com/sbryngelson/ANEForge/blob/caeef8edf13b9ec7a3338826daaa27f99e1663d1/bench/results/compress_speedup_bench.json), [measurement code](https://github.com/sbryngelson/ANEForge/blob/caeef8edf13b9ec7a3338826daaa27f99e1663d1/bench/compress_speedup_bench.py#L17).
- The identified ANEForge M4 roofline is a **base M4 MacBook Air, 16 GB, macOS 26.2**, source commit `23ef10a6c370b5a5aa9099429d8686e60ada0533`. Its bandwidth suite measures activation operations such as ReLU, not this FFN's static weight stream, and includes no corresponding compression comparison. It cannot establish a physical M4 Max/macOS 15.6 ANE weight ceiling. [Machine and measurements](https://github.com/sbryngelson/ANEForge/blob/caeef8edf13b9ec7a3338826daaa27f99e1663d1/bench/results/rooflines/roofline-apple-m4-Mac16_12-d4109cd41a75-6779bad2.json).

Current 150 ms for 48 FFNs corresponds to approximately **113.25 GB/s of logical FP16 source weights** using the [verified budget](/Users/george/Downloads/rvllm/v3/reports/gemma4-12b-evidence-20260914/weight-budget.json). It is not a measured bus counter. On an illustrative 250 ms compute path with 150 ms in FFNs, a 1.16× FFN improvement yields about 229 ms total; even a 2× FFN improvement yields 175 ms. Dispatch fusion alone cannot account for the missing bandwidth.

## Priority and one bounded optional follow-up

1. **Finish INT8 full-model quality/timing first**, keeping tanh GELU, imported KV, norms, and phased residency unchanged. No inspected evidence justifies delaying it for compiler-option hunting. Preserve the exact reconstructed-weight control when interpreting component gains.
2. If a further encoding experiment is warranted, test **LUT8 representing the existing INT8 reconstruction exactly** on one FFN. This isolates affine-versus-palette lowering without accepting additional quantization error: indices `uint8[N,K,1,1] = q + 128` using widened integer arithmetic; LUT `fp16[N,1,1,1,256,1]`, where entries 1–255 use `fp16((j−128) * stored_scale[n])` with the current FP32 multiplication and FP16 rounding. Set unused entry 0 to zero: rvllm clamps q to −127…127. The iOS18 op accepts uint8 indices, 256 entries, rank+2 LUTs, and divisibility-based groups. [Exact op contract](https://github.com/apple/coremltools/blob/181cbd341fa394ea53fd6895a2e0a46aaec27cb1/coremltools/converters/mil/mil/ops/defs/iOS18/compression.py#L269). Compare against the same INT8 and reconstructed FP16 controls; preserve the three-convolution graph.

This second experiment is **a proposed MIL-valid representation, not demonstrated private-ANE compilation or acceleration**. Its many row codebooks may be slow or rejected; they add 17,694,720 source bytes across the three FFN matrices, about 10% over the INT8 element payload. Exact reconstruction and unchanged model error can be checked before hardware work. If the current INT8 path meets the goal, this experiment need not run. Neither invented private flags nor W8A8 activation quantization is a lower-cost established route to the requested weight-only improvement.
