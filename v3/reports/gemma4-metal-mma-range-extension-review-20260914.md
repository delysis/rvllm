# Gemma 4 12B MMA32: M6 and M64–1024 extension review

2026-09-14. Source-only review; no edits to implementation, builds, hardware, or cache operations. The existing M20–32 path is qualified. Wider eligibility is a proposed extension, not a performance or numerical result.

**Recommendation:** reuse the existing 32×32×32 BF16/FP32 matrix kernel unchanged. Extend its opt-in routing in two stages: M6 first, then M64–1024. The essential change for the latter is routing **O/down through separate MMA projection and RMSNorm**, with matching encoder accounting and numeric-ABI identity. Changing only the matrix shape predicate is insufficient.

For the ordinary dense, untraced 12B layer, M6 adds one QKV projection encoder relative to its current fused-QKV route; O/down already use split normalization. M64+ adds three encoders: QKV projection, separate O RMSNorm, separate down RMSNorm. Across 48 layers those are **+48 / +144 layer encoders**, respectively. They remain inside the same prefill command buffer. These are source-derived deltas, not measured overhead.

One scope trap: `M` is total token rows, not necessarily one prompt. QKV already checks `MetalPhase::Prefill` at line 716, but ordinary GEMM selection has no phase argument. Adding M6 could also change a six-sequence decode batch when this environment flag is used in the generic runtime. For a strictly prefill-only extension, pass a resolved prefill-MMA route into ordinary projection encoding/accounting; otherwise document that the opt-in is confined to the single-request disaggregated CLI until batched decode is qualified.

## Precision boundaries that must survive

**QKV:** keep `qkv_project_f32_mma32` output in FP32 until the existing [head norm/RoPE/cache epilogue](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:1003). It reads row-major `[M,N]` at `token*N + projection_row`, computes head RMS on FP32, rounds the normalized value to BF16, then applies the established partial RoPE and cache stores. Global layers retain raw-K-as-V projection and the 9216 packed width. Do not reuse the BF16 GEMM entry point here.

**Gate/up, O, down:** retain FP32 accumulation followed by one BF16 projection store through [gemm_f16_mma32](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:577). Its BF16 source rewrite removes FP16 saturation and changes `half` matrix operands to `bfloat` at [kernels.rs:2535](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:2535). O/down then use existing RMSNorm on that BF16 tensor, followed by the unchanged residual operations. Relevant call sites are [O](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:1468) and [down](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:1802).

**Important baseline difference:** the current long-M [fused projection/RMS kernel](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:624) computes RMS from unrounded FP32 projection values. The qualified short-M split path rounds projection to BF16 first. Therefore extended O/down results need an independent BF16 projection→RMS oracle; strict equality to the long-M fused fallback is not the correctness criterion. A GEMM-only component comparison cannot validate this boundary.

Update the [Metal numeric-ABI routing marker/version](/Users/george/Downloads/rvllm/v3/crates/rvllm-runtime/src/apple_metal_backend.rs:339). The fingerprint hashes shader source and the MMA environment flag, but widening Rust-only dispatch conditions does not change either. Without a new routing marker/version, cached KV from different long-M numerical paths could have the same fingerprint.

## Kernel and scratch bounds

The [existing tile implementation](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/kernels.rs:509) already masks A/B loads, masks C stores, and executes uniform barriers across four SIMD groups. Its grids are `ceil(M/32) × ceil(N/32)`, 128 threads. A/B are `[M,K]` / `[N,K]`; C has logical row stride N, never padded to 32. All listed dimensions through M1024 fit its uint indexing. It needs 8 KiB threadgroup storage, independent of M; no additional global MMA workspace or weight repacking is required. M6 uses only 6/32 rows of one tile, so its speed benefit needs measurement. Do not pad the logical prompt with extra tokens.

[Planning](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/gemma4_model.rs:1596) and [allocation](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/gemma4_model.rs:2360) already size exact-12B QKV scratch at four bytes per element using `max_batch_tokens`. At M1024, max packed width 9216 needs **37,748,736 bytes (36 MiB)**. Preserve the four-byte [planar-overlap check](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/layer_forward.rs:253), correct execution-slot rebinding, and admission `M <= max_batch_tokens`. Region sizing must use configured capacity rather than the former 32-token assumption.

Longer admission also enlarges existing non-MMA buffers: [logits and argmax partial arrays](/Users/george/Downloads/rvllm/v3/crates/rvllm-apple-metal/src/gemma4_model.rs:1536) reserve 512 MiB plus 256 MiB per execution slot at M1024, even though this handoff samples only the final prompt row. This is an observed sizing policy, not an MMA regression. Keep the actual prompt-sized `MAX_BATCH_TOKENS` configuration. Optimizing final-row-only storage should be a separate change.

## Residency correction

Earlier reports' implication that coexistence itself caused a measured hardware memory/performance penalty was too strong. Source establishes that retaining both owners retains both sets of allocations; historical sequential timings and swap observations were confounded by host load and do **not** establish the causal cost of coexistence. Preserve the existing phased policy as a controlled baseline for this routing change, not as a proven universal requirement. Any later comparison needs paired/rotating same-workload runs with consistent cache state, warm-up and host-load recording, plus actual residency/swap/page-fault measurements. This review makes no coexistence penalty claim.
